# AI Code Suggestion Lifecycle Tracking

## Overview

The Firm Harness lifecycle tracking system provides **AI provenance tracking** for all code suggestions generated by the coding assistant. This system tracks every AI-generated code proposal from the moment it's suggested through to being shipped in a git commit.

**This is provenance tracking, not surveillance.** The goal is to understand how AI-generated code moves through your development workflow - acceptance rates, modification patterns, and shipping velocity. This data helps teams make informed decisions about AI assistance effectiveness.

---

## The Four Lifecycle States

Every AI-generated code suggestion moves through one of two paths:

### Happy Path: Proposed → Accepted → Shipped

1. **📝 Proposed**
   - A code suggestion is generated and scanned
   - Recorded with full context: model, scan results, files, diffs
   - Waiting for user decision

2. **✅ Accepted**
   - User approved the suggestion and it was written to disk
   - Files are now in the working directory
   - Ready to be committed

3. **🚀 Shipped** (Clean Match)
   - Code was committed to git with no modifications
   - Detected via exact SHA-256 hash match
   - Represents 100% AI-generated code in production

4. **🔧 Shipped (Modified)** (Fuzzy Match)
   - Code was committed but modified before shipping
   - Detected via 80%+ line similarity within 7 days
   - Represents AI-assisted code with human refinement

### Rejection Path: Proposed → Discarded

**🗑️ Discarded** - Suggestion was rejected for one of four reasons:

- **Scan Failure**: Security scan detected critical issues, user rejected override
- **User Rejection**: User explicitly rejected the suggestion
- **Policy Denial**: Organization policy blocked the write
- **Abandonment**: Session ended with suggestion still proposed

---

## State Transitions

### Legal Transitions

```
proposed → discarded
proposed → accepted
accepted → shipped
accepted → shipped-modified
```

### Illegal Transitions

All terminal states (discarded, shipped, shipped-modified) cannot transition further.  
You cannot go from discarded → accepted.  
You cannot go from proposed → shipped (must be accepted first).

The state machine enforces these rules automatically.

## Git Hook Installation

### Installing Hooks

```bash
opencode lifecycle install-hooks
```

This installs two git hooks:
- **post-commit**: Runs after every commit
- **post-rewrite**: Runs after rebase/amend operations

Both hooks invoke the shipped-detection script automatically.

### Behavior

- **Never blocks commits** - all errors are caught and logged
- **Detects existing hooks** - warns before overwriting
- **Prepend mode** - use `--force` to prepend to existing hooks
- **Logs to `.firm-harness/logs/shipped-detection.log`**

### Uninstalling Hooks

```bash
opencode lifecycle uninstall-hooks
```

- Removes firm-harness tracking code
- Preserves other hook logic

### Checking Status

```bash
opencode lifecycle hooks-status
```

Shows which hooks are installed and whether other hooks exist.

## Shipped Detection

### How It Works

The shipped-detection script runs automatically after every commit:

1. **Get HEAD commit SHA** and list of changed files
2. **For each changed file:**
   - Read content at HEAD
   - Compute SHA-256 hash
   - **Try Clean Match First:**
     - Query for accepted suggestions with matching content hash
     - If found → mark as `shipped` with commit SHA
   - **Fall Back to Fuzzy Match:**
     - Query recent accepted suggestions for same file (last 7 days)
     - Extract added lines from suggestion's diff
     - Count how many lines appear in current file
     - If ≥80% match → mark as `shipped-modified` with commit SHA

3. **Log results** to `.firm-harness/logs/shipped-detection.log`

### Matching Thresholds

- **Clean Match**: 100% exact SHA-256 hash match
- **Fuzzy Match**: ≥80% of suggested lines present verbatim
- **Time Window**: Only considers suggestions from last 7 days

### Error Handling

- All errors are caught and logged
- Script always exits with status code 0
- Never blocks or delays commits

## Privacy & Framing

### This Is Provenance Tracking, Not Surveillance

**What This System Tracks:**
- Which AI suggestions were proposed
- Which were accepted and written to disk
- Which were eventually shipped in commits
- Model performance and acceptance rates

**What This System Does NOT Track:**
- Time spent reviewing code
- Keyboard activity or idle time
- Individual developer "productivity scores"
- Any data outside the git repository

### The Data Never Leaves Your Machine

- All data stored in `.firm-harness/lifecycle.db` (local SQLite)
- No network calls beyond existing LLM gateway
- No GitHub API usage
- No external analytics services

### Use Cases

**For Developers:**
- "Did that AI suggestion I accepted last week actually ship?"
- "Which model gives me the highest ship rate?"
- "How many of my AI suggestions need modification before shipping?"

**For Teams:**
- "What's our AI code acceptance rate this sprint?"
- "Are we shipping more AI-generated code over time?"
- "Which types of suggestions get modified most often?"

**For Compliance:**
- "Show me the complete audit trail for this AI-generated function"
- "What scan findings were present when this code was proposed?"
- "Which suggestions were rejected due to security scans?"

## CLI Commands

### Inspect a Suggestion

```bash
opencode lifecycle inspect <suggestion-id>
```

Prints the complete regulatory artifact for a suggestion:
- Basic info (ID, session, timestamps, status)
- Model and provider
- Security scan results and findings
- All files with diffs
- Complete state transition log

**Short IDs work too:**
```bash
opencode lifecycle inspect abc12345
```

### View Statistics

```bash
opencode lifecycle stats
```

Shows summary for last 7 days:
- Total proposed, accepted, shipped
- Acceptance and shipping rates
- Discard breakdown by reason
- Per-model performance

**Options:**
```bash
# Custom time window
opencode lifecycle stats --window 14

# Filter by session
opencode lifecycle stats --session <session-id>
```

### Watch Live Events

```bash
opencode lifecycle watch
```

Polls the database every 2 seconds and prints events as they happen:
```
[14:23:05] 📝 PROPOSED | abc12345 | openai/gpt-4 | 3 files, scan: pass
[14:23:12] ✅ ACCEPT   | abc12345 | openai/gpt-4 | 3 files
[14:25:30] 🚀 SHIP     | abc12345 | openai/gpt-4 | commit: a7f3c21
```

Great for demos - run in a second terminal pane to show real-time lifecycle transitions.

## Direct Database Queries

The lifecycle database is just SQLite at `.firm-harness/lifecycle.db`.  
You can query it directly for custom analysis:

### Example Queries

**Find all suggestions from a specific model:**
```sql
SELECT id, status, created_at, scan_status
FROM suggestions
WHERE model = 'gpt-4' AND provider = 'openai'
ORDER BY created_at DESC;
```

**Calculate acceptance rate by model:**
```sql
SELECT 
  model,
  provider,
  COUNT(*) as proposed,
  SUM(CASE WHEN status IN ('accepted', 'shipped', 'shipped-modified') THEN 1 ELSE 0 END) as accepted,
  ROUND(100.0 * SUM(CASE WHEN status IN ('accepted', 'shipped', 'shipped-modified') THEN 1 ELSE 0 END) / COUNT(*), 1) as acceptance_rate
FROM suggestions
GROUP BY model, provider;
```

**Find suggestions that failed security scans but were shipped anyway:**
```sql
SELECT s.id, s.scan_status, s.commit_sha, COUNT(sf.id) as file_count
FROM suggestions s
JOIN suggestion_files sf ON s.id = sf.suggestion_id
WHERE s.scan_status = 'fail' 
  AND s.status IN ('shipped', 'shipped-modified')
GROUP BY s.id;
```

**Show transition timeline for a suggestion:**
```sql
SELECT 
  from_status,
  to_status,
  reason,
  datetime(transitioned_at / 1000, 'unixepoch') as timestamp
FROM status_transitions
WHERE suggestion_id = '<your-id>'
ORDER BY transitioned_at;
```

**Files with highest modification rate:**
```sql
SELECT 
  sf.file_path,
  COUNT(*) as times_suggested,
  SUM(CASE WHEN s.status = 'shipped' THEN 1 ELSE 0 END) as clean_ships,
  SUM(CASE WHEN s.status = 'shipped-modified' THEN 1 ELSE 0 END) as modified_ships,
  ROUND(100.0 * SUM(CASE WHEN s.status = 'shipped-modified' THEN 1 ELSE 0 END) / 
    NULLIF(SUM(CASE WHEN s.status IN ('shipped', 'shipped-modified') THEN 1 ELSE 0 END), 0), 1) as modification_rate
FROM suggestions s
JOIN suggestion_files sf ON s.id = sf.suggestion_id
WHERE s.status IN ('shipped', 'shipped-modified')
GROUP BY sf.file_path
HAVING times_suggested > 1
ORDER BY modification_rate DESC;
```

**Suggestions abandoned in the last week:**
```sql
SELECT id, session_id, created_at, model
FROM suggestions
WHERE status = 'discarded'
  AND discard_reason = 'abandonment'
  AND created_at > (strftime('%s', 'now') - 604800) * 1000
ORDER BY created_at DESC;
```

## Database Schema

### suggestions
- `id` (TEXT, primary key)
- `session_id` (TEXT)
- `created_at` (INTEGER, unix timestamp ms)
- `model` (TEXT)
- `provider` (TEXT)
- `prompt_hash` (TEXT, SHA-256)
- `user_identity` (TEXT, nullable)
- `status` (TEXT: proposed | discarded | accepted | shipped | shipped-modified)
- `discard_reason` (TEXT, nullable)
- `commit_sha` (TEXT, nullable)
- `shipped_at` (INTEGER, nullable, unix timestamp ms)
- `scan_status` (TEXT: pass | warn | fail, nullable)
- `scan_findings` (BLOB, JSON, nullable)

### suggestion_files
- `id` (INTEGER, primary key autoincrement)
- `suggestion_id` (TEXT, foreign key → suggestions)
- `file_path` (TEXT)
- `old_content_hash` (TEXT, SHA-256, nullable)
- `new_content_hash` (TEXT, SHA-256)
- `lines_added` (INTEGER)
- `lines_removed` (INTEGER)
- `diff_text` (TEXT, unified diff)

### status_transitions
- `id` (INTEGER, primary key autoincrement)
- `suggestion_id` (TEXT, foreign key → suggestions)
- `from_status` (TEXT, nullable for initial transition)
- `to_status` (TEXT)
- `reason` (TEXT, nullable)
- `transitioned_at` (INTEGER, unix timestamp ms)

### Indexes
- `idx_suggestions_status` on `suggestions(status)`
- `idx_suggestions_session_id` on `suggestions(session_id)`
- `idx_suggestion_files_new_content_hash` on `suggestion_files(new_content_hash)`
- `idx_suggestion_files_file_path` on `suggestion_files(file_path)`
- `idx_status_transitions_suggestion_id` on `status_transitions(suggestion_id)`

## FAQ

**Q: Does this slow down my workflow?**  
A: No. Lifecycle tracking happens asynchronously and never blocks writes or commits.

**Q: Can I disable it?**  
A: Yes. Uninstall the git hooks with `opencode lifecycle uninstall-hooks`. The pipeline integration will still record proposed/accepted states, but shipped detection won't run.

**Q: What if I rebase or amend commits?**  
A: The `post-rewrite` hook handles this automatically.

**Q: How much disk space does the database use?**  
A: Typically <1MB per 1000 suggestions. Diffs and scan findings are stored as text/JSON.

**Q: Can I delete old data?**  
A: Yes, the database is just SQLite. Run `DELETE FROM suggestions WHERE created_at < <timestamp>` to clean up old records. Foreign key cascades will delete associated files and transitions automatically.

**Q: What happens if the database is corrupted?**  
A: Delete `.firm-harness/lifecycle.db` and it will be recreated on next use. Historical data will be lost, but tracking will continue normally.

**Q: Can I export the data?**  
A: Yes. Use SQLite tools to export: `sqlite3 .firm-harness/lifecycle.db .dump > backup.sql`

## Troubleshooting

**Shipped detection not running:**
1. Check hooks are installed: `opencode lifecycle hooks-status`
2. Check logs: `cat .firm-harness/logs/shipped-detection.log`
3. Reinstall hooks: `opencode lifecycle install-hooks --force`

**No suggestions showing in stats:**
1. Verify database exists: `ls -la .firm-harness/lifecycle.db`
2. Check suggestions were recorded: `sqlite3 .firm-harness/lifecycle.db "SELECT COUNT(*) FROM suggestions;"`
3. Verify working directory matches project root

**Inspection shows "Suggestion not found":**
1. Use full suggestion ID (not short ID) for now
2. Verify you're in the correct project directory
3. Check database exists: `ls .firm-harness/lifecycle.db`
